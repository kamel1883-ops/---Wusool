# البنية المعمارية — وصول

## ١. نظرة عامة

```
┌──────────────────────────────────────────────────────────────────────┐
│ Browser — React SPA (AR/RTL + EN/LTR)                                │
│ جلسة عبر Cookie HttpOnly + ترويسة x-wusool-client لكل طلب تعديل      │
└──────────────────────────────┬───────────────────────────────────────┘
                               │ HTTPS
┌──────────────────────────────▼───────────────────────────────────────┐
│ Cloudflare Worker — Hono                                            │
│  رؤوس أمان · فحص Origin · CSRF · تحديد معدل محاولات الدخول           │
│                                                                      │
│  /api/public, /api/setup, /api/auth/*      (عام + جلسة)              │
│  /api/company/:companyId/*                 (عضوية شركة + صلاحية)      │
│  /api/admin/*                              (Super Admin فقط)          │
└───────────┬──────────────────────────────────────┬───────────────────┘
            │                                      │
     ┌──────▼───────┐                      ┌───────▼────────┐
     │ D1 (SQLite)  │                      │ R2 (private)   │
     │ tenants/…    │                      │ إثباتات تحويل  │
     └──────────────┘                      │ عقود لاحقًا    │
                                           └────────────────┘
```

لا يوجد أي اتصال مباشر من المتصفح بقاعدة البيانات أو بالتخزين أو بمزوّدي الذكاء الاصطناعي.
كل شيء يمر عبر الـ Worker الذي يملك الصلاحيات.

## ٢. عزل العملاء (Multi-Tenancy)

القاعدة الحاكمة: **هوية الشركة تُشتق من عضوية المستخدم، لا من الطلب.**

1. `requireAuth` يحمّل المستخدم من الجلسة فقط.
2. `companyContext` يقرأ `:companyId` من المسار، ويتحقق من وجود عضوية نشطة
   لهذا المستخدم في هذه الشركة، ثم يضع الشركة والدور في سياق الطلب.
3. كل استعلام داخل مساحة العميل يُقيَّد بـ `company.id` المأخوذ من السياق.
4. مسارات الإدارة محمية بـ `requireSuperAdmin` ولا تقبل أي `companyId` مؤثر على الصلاحية.
5. الجلسات تُلغى تلقائيًا عند تعليق الشركة أو تعطيل المستخدم.

تم التحقق عمليًا: مالك الشركة (أ) يطلب بيانات الشركة (ب) → `403`، ومالك شركة لا يستطيع
استخدام `/api/admin/*` → `403`.

## ٣. المصادقة والجلسات

- كلمة المرور: **PBKDF2-SHA256**، ٢١٠٬٠٠٠ تكرار، ملح عشوائي ١٦ بايت لكل مستخدم.
- الجلسة: توكن عشوائي ٣٢ بايت، يُخزَّن **Hash فقط** في `sessions`، صلاحية ٧ أيام.
- Cookie: `HttpOnly`, `SameSite=Lax`, `Secure` تلقائيًا على HTTPS.
- تغيير كلمة المرور يُبقي الجلسة الحالية ويلغي بقية الجلسات.
- الحسابات المنشأة بكلمة مرور مؤقتة (`must_change_password = 1`) لا تستطيع استخدام المنتج قبل
  تعيين كلمة مرور خاصة — مفروض على الخادم.
- حد محاولات الدخول: ٨ محاولات فاشلة لكل بريد خلال ١٥ دقيقة → `429`.
- لا توجد كلمات مرور أو مفاتيح في الكود: أول حساب مدير يُنشأ من `/setup` ولا يمكن تكراره.

## ٤. دورة الاشتراك

```
Pending ──(اعتماد إثبات تحويل)──► Active ──(انتهاء التاريخ)──► Expired
   │                                │
   └── Suspended ◄──────────────────┘        Cancelled (نهائي)
```

- الحالة الفعلية تُحسب عند القراءة: شركة `active` انتهى تاريخها تُعرض `expired` فورًا.
- `subscription.warning_days` (افتراضي ٣٠) يضبط التنبيه قبل الانتهاء.
- الميزات التي تتطلب اشتراكًا فعّالًا (مثل إضافة أعضاء، وفي المراحل القادمة التحليل والتوليد)
  محجوبة على الخادم بحالة `402 subscription_inactive`.
- الفوترة في هذه المرحلة يدوية: `invoices` + `payment_proofs`، والاعتماد يحدّث الفاتورة إلى
  `paid` والشركة إلى `active` مع تواريخ الفترة.
- الحقول المالية والخطة والحالة **لا يكتبها العميل أبدًا** — فقط Super Admin.

## ٥. الملفات الحساسة

- R2 خاص، المفاتيح بالشكل `payment-proofs/{companyId}/{invoiceId}/{proofId}.{ext}`.
- التحقق على الخادم: النوع (PNG/JPEG/WebP/PDF) والحجم (≤ ٥MB) قبل التخزين.
- القراءة عبر مسارين محميّين فقط: `/api/admin/proofs/:id/file` (إدارة) و
  `/api/company/:id/proofs/:proofId/file` (عضوية + صلاحية فوترة)، مع `no-store`.
- العقود لاحقًا في نفس النهج (وصول خاص + استخراج بيانات بمراجعة بشرية).

## ٦. طبقة الذكاء الاصطناعي (تصميم جاهز للمرحلة الثالثة)

لا يوجد أي استدعاء لنموذج في المرحلة الأولى. التصميم المعتمد:

```
مهمة (تحليل/محتوى/صورة)
   └── AiProvider (واجهة موحّدة: name, generateStructured, generateImage, cost estimate)
         ├── OpenAI-compatible (OpenAI / Gemini / Llama عبر بوابة)
         ├── Anthropic
         └── MockProvider (تطوير فقط، مخرجات واضحة أنها تجريبية)
```

- كل مزوّد يُعرّف في `ai_providers` (اسم، نموذج أساسي واحتياطي، حد طلبات، حد تكلفة، إعدادات،
  مفتاح في Secrets لا في الجدول).
- كل استدعاء يمر عبر مزوّد مسجّل في `usage_events` (نوع العملية، النموذج، التكلفة) — وهي جاهزة
  الآن وتظهر فارغة في لوحة الاستخدام.
- المخرجات المنظمة JSON Schema وتُخزَّن مع **تصنيف المصدر** لكل حقل:
  `extracted` / `inferred` / `suggestion` / `unavailable` حتى لا تُعرض استنتاجات كحقائق.
- إعادة التوليد تُنشئ نسخة جديدة ولا تستبدل السابقة.

## ٧. الاعتماد البشري (مبدأ غير قابل للتعطيل)

كل مادة (منشور/تصميم/حملة/رسالة) تمر بحالات:

```
Draft → In Review → (Changes Requested → Draft) → Approved → Scheduled → Published → Archived
```

- لا نشر ولا إرسال ولا تشغيل أتمتة قبل `Approved`.
- يُسجَّل في `audit_logs`: من أنشأ، من عدّل، من طلب التعديل، من اعتمد، تاريخ الاعتماد، رقم النسخة،
  ومن أرسل/نشر بعد ذلك.
- في المرحلة الأولى هذا مطبّق على **إثباتات التحويل والفواتير** (لا اعتماد = لا تفعيل)، والبنية
  نفسها تُستخدم لوحدات المحتوى في المرحلة الثالثة.

## ٨. الواجهة والهوية

- اللغات: `ar` (RTL، افتراضي) و`en` (LTR) من قاموس واحد `src/lib/i18n.ts`؛ كل رسالة خطأ من الـ API
  لها مفتاح ترجمة معروض للمستخدم.
- الألوان والاسم والشعار من `platform_settings` وتُحقن كمتغيرات CSS (`--brand`, `--ink`) عند تحميل
  الجلسة، فلا حاجة لإعادة بناء عند تغيير الهوية.
- الحالات (Subscription/Invoice/Proof) تُعرض دائمًا بشكل موحّد عبر مكوّن `StatusBadge`.
- لا زخرفة زائدة، شبكة لوحة تحكم عملية، متجاوبة حتى ٣٦٠px.

## ٩. الأمان — قائمة تحقق

| البند | الحالة |
| --- | --- |
| عزل بيانات المستأجرين | ✅ على مستوى الاستعلام والمسار |
| تشفير/تجزئة كلمات المرور | ✅ PBKDF2-SHA256 |
| جلسات آمنة (HttpOnly/SameSite/إلغاء) | ✅ |
| CSRF | ✅ SameSite + ترويسة عميل + فحص Origin |
| XSS | ✅ React escaping + لا `dangerouslySetInnerHTML` |
| SQL Injection | ✅ استعلامات مُعاملة (Bound parameters) فقط |
| تحقق من الملفات المرفوعة | ✅ نوع + حجم + تخزين خاص |
| Rate limiting | ✅ محاولات الدخول؛ يُوسّع لباقي المسارات مع المراحل |
| سجل تدقيق | ✅ `audit_logs` |
| صلاحيات على الخادم لا الواجهة | ✅ `requireAuth` / `companyContext` / `requireSuperAdmin` / `can()` |
| إخفاء الأسرار | ✅ لا مفاتيح في الواجهة؛ الأسرار تُدار كـ Secrets عند النشر |
| نسخ احتياطية | ⏳ سياسة الاستضافة (D1 backup / تصدير دوري) |
| تصدير/حذف بيانات العميل | ⏳ ضمن سياسة الخصوصية قبل الإطلاق التجاري |
| عدم استخدام البيانات للتدريب | ✅ مذكور في سياسة الخصوصية |

## ١٠. قرارات معمارية

1. **Worker + D1 + R2** بدل خادم Node دائم: مناسب للاستضافة المُدارة، بلا إدارة خوادم.
2. **بلا مكتبة UI**: هوية قابلة للتغيير بالكامل من قاعدة البيانات دون تحديث حزم.
3. **جلسات قاعدة بيانات** بدل JWT: إلغاء فوري عند التعليق أو تغيير الصلاحيات.
4. **كلمة مرور مؤقتة تُعرض مرة واحدة** بدل بريد دعوة: لا يوجد مزوّد بريد بعد، والمخرَج آمن
   وقابل للتسليم بقناة موثوقة.
5. **الحالة الفعلية للاشتراك محسوبة**: لا حاجة لمهمة مجدولة يومية لتحديثها.
6. **لا بيانات وهمية**: بيانات الدعم والبنك والشركة المالكة تبدأ فارغة وتُعرَّف من الإدارة.
