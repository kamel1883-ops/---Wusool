# مراجعة المرحلة الثانية — تحليل المواقع

مراجعة تنفيذ المرحلة الثانية قبل الانتقال إلى الثالثة. كل بند أدناه تحقق منه اختبار فعلي
عبر HTTP على `wrangler dev` مع قاعدة D1 محلية جديدة (`npm test`، ٥٨ فحصًا)، لا بالاطلاع على الكود فقط.

## ١. جدول المراجعة

| البند | كيف تُحقّق منه | النتيجة |
| --- | --- | --- |
| عزل بيانات الشركات | مالك شركة ب يطلب قائمة/تفاصيل/تعديل تحليل شركة أ | ✅ `403` في الحالات الثلاث |
| الشركة تُشتق من العضوية | كل مسار يمرّ بـ `companyContext` ويقيّد الاستعلام بـ `company_id` من السياق | ✅ لا مسار يقبل `companyId` من الجسم |
| الصلاحيات على الخادم | زائر/كاتب محتوى/مدير تسويق يحاولون إنشاء أو تعديل أو اعتماد | ✅ `403` لكل حالة غير مسموحة |
| حدود الاشتراك | شركة منتهية تنشئ تحليلًا | ✅ `402 subscription_inactive` |
| حالات التحليل | `draft → queued → crawling → extracting → analyzing → awaiting_review → approved` | ✅ تُخزَّن وتُعرض في الواجهة |
| طلب التعديل والاعتماد | `request-changes` بدون تعليق / مع تعليق، ثم `submit-review` ثم `approve` | ✅ `422` ثم انتقال الحالات بشكل صحيح |
| حفظ النسخ | تعديل نتيجة ثم قراءة النسخة ١ | ✅ النسخة السابقة باقية كما هي |
| الاعتماد البشري | تعديل تقرير معتمد | ✅ يُنشئ نسخة جديدة ويعيده إلى `awaiting_review` ويمسح `approved_version` |
| عدم تسريب المفاتيح | فحص أجسام الاستجابات لكلمات `AI_API_KEY` و`CRAWLER_API_TOKEN` و`sk-` | ✅ لا تظهر في أي استجابة |
| حماية الموارد الخاصة | صفحة محمية (401/403) تُسجَّل `blocked` ولا تُقرأ؛ صفحة الزحف الخام للمشاهدين | ✅ `403` لغير المراجعين |
| منع الوصول لشبكة داخلية | `http://127.0.0.1/admin` | ✅ `422` |
| احترام robots.txt | `robots.txt` يُقرأ ويُطبَّق على المسارات (زاحف `fetch`) | ✅ منفّذ، ويُسجَّل `robots_policy` |
| حدود الصفحات والعمق | طلب `maxPages=999` | ✅ يُقصّ إلى الحد الأقصى (٤٠) |
| منع الحمل الزائد | تعديل حد الساعة إلى ١ ثم إنشاء تحليلين | ✅ الثاني يعيد `429` |
| فشل المزوّد وإعادة المحاولة | تحويل المزوّد إلى `openai` بدون مفتاح ثم إعادة الوضع التجريبي | ✅ `ai_provider_not_configured` ثم نجاح إعادة المحاولة |
| الإلغاء | إلغاء مسودة ثم محاولة الإلغاء مرة أخرى | ✅ `200` ثم `409` |
| سجل التدقيق | قراءة `/api/admin/audit?action=site_analysis` | ✅ `created`/`approved`/`failed` مسجّلة |
| العربية والإنجليزية وRTL/LTR | قاموس واحد لكل النصوص الجديدة + `dir` من الجلسة | ✅ لا نص مكتوب داخل المكوّنات |
| TypeScript وBuild | `npm run check` و`npm run build` | ✅ بلا أخطاء |

## ٢. المشاكل التي وُجدت أثناء المراجعة وأُصلحت

1. **عدّاد التزامن كان يعدّ المهمة نفسها.** عند بدء التحليل تُوضع الحالة `queued` ثم يعيد خط
   التنفيذ فحص التزامن فيرى نفسه ويُعيد `analysis_in_progress`. أُصلح باستثناء معرّف المهمة
   الحالية في الفحص (`checkConcurrency`)، مع إبقاء فحص المعدل في مسار الإنشاء.

2. **المعلومات الناقصة لم تُدرج في `missing_information`.** الوضع التجريبي كان يفحص الحقول
   المفردة فقط، فيظهر «القيمة المقترحة: غير متوفر» دون إدراجه في قائمة النواقص. أُصلح بمسح
   كل الحقول والقوائم التي مصدرها `missing` وإدراجها كأسئلة للعميل.

3. **ترتيب التحقق في `request-changes`.** كان يفحص الحالة قبل التعليق، فيُعيد `invalid_status`
   بدل `comment_required` عند إعادة المحاولة. صار الاختبار يتحقق من الحالتين كلٍّ في موضعه.

4. **`capabilities.edit` للتقارير المعتمدة.** كانت الواجهة تمنع التعديل بينما الخادم يسمح به
   ويُعيد فتح المراجعة. صارا متطابقين، مع تنبيه واضح في الواجهة أن الاعتماد لا يُورَّث.

5. **حالة الواجهة بعد الاعتماد.** كان زر التعديل يختفي دون تفسير؛ أُضيف شريط حالة
   (`معتمد` / `غير معتمد` + رقم النسخة) وتنبيه «إعادة الفتح».

6. **ثبات الاختبارات.** كانت الاختبارات تستخدم منفذًا عشوائيًا قد يشغله خادم قديم، فيقرأ
   قاعدة بيانات أخرى. صار المنفذ يُحجز فعليًا (bind على 0) ويُقتل شجرة العملية كاملة بعد الاختبار.

## ٣. ما يبقى خارج هذه المرحلة (مقصود)

- لا بريد ولا WhatsApp ولا CRM ولا تصاميم ولا ربط Google/Meta Ads.
- لا نشر ولا إرسال خارجي: كل المخرجات تبقى داخل المنصة حتى `approved`، ولا وظيفة إرسال أصلًا.
- لا مفاتيح حقيقية في المستودع: `MockAIProvider` و`MockCrawlerProvider` هما الافتراضي.
